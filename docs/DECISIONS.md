| D40 | The running item's progress: SubSync's live stage ("Reading audio…", "Listening…", "Matching lines…") plus a share of the bar. With SubSync 1.3.0 `--progress`, during listening the share is listening's expected slice of the run filled by SubSync's own `percent` (the server sends it as `percent`); otherwise, and for 1.2.0, it is elapsed time over an expected time. The bar holds below 95% until the item ends and never moves backwards. The expected time is start-up plus the video's length times a speed ratio learned from finished runs on this server (before the first: 0.04 if the last run said GPU, else 0.33, plus 15 s start-up). From 1.3.0 runs it learns start-up as the process's wall time minus `read_audio + listen + match` (`model_load_seconds` when the wall time is missing), reading and listening per second of video, and matching seconds. Runs whose transcript came from SubSync's cache teach nothing: 1.3.0 says so (`timings.from_cache`, or a run that never reached reading audio or listening), and without timings a run under 1% of the video's length or under 10 s is taken as cached | Owner reported (2026-11-11: "the progress bar was just stuck on 0%"); 1.3.0 use and the cached-run fix 2026-11-12 (owner approved the start-up formula and the 1% / 10 s rule) | SubSync 1.2.0 prints no percentage, and the bar only counted finished items, so one item showed 0% for its whole run. A cached run (a Retry from the failed-syncs log, or a re-sync after a no-match) takes a few seconds and dragged the learned ratio far too low. Start-up from wall time rather than `model_load_seconds`: 1.3.0 reads the audio while the model loads, so adding both would count that overlap twice, and `model_load_seconds` leaves out the self-check and Python start. 1% rather than 2%: a fast GPU can finish a 45-minute episode near 2% of its length, and a cached run is a few seconds, far below 1% (27 s). Everything lives in memory and resets on restart; a wrong guess only moves the bar, never the time limit (D34). With piped output SubSync 1.2.0 writes the stage lines only to its `logs\cli.log`, not to stdout (verified 2026-11-12), so for 1.2.0 the worker follows that file during a run (`LogTail`); only one SubSync runs at a time, so its new lines are ours. With 1.3.0 the `PROGRESS` lines on stdout replace it |

| D45 | One `subsync-cli serve --overwrite [--keep-layout] [--cpu]` per queue run, with up to two items in it, instead of one `sync` per episode (replaces D5) | Owner approved (2026-11-12), with the two changes below | **One process:** started for the first item of a queue run (SubSync 1.3.0 or later), closed through stdin when the queue is empty (SubSync finishes, exits 0; ended after 30 s if not). Restarted when Tidy up lines, Force CPU or the SubSync folder change: no item is sent ahead then, and the next one starts a new process once the current one is finished. **Per item, unchanged rules:** re-validate, back up and journal *before* the request is sent (SubSync may start at once), request `output` = the subtitle itself, then verify, swap or restore, record and refresh on its `result`. **Overlap:** when the only item in SubSync reaches `listening`, the next eligible one is backed up and sent, so at most two are in SubSync and its audio is read meanwhile. Items that are skipped or fail before SubSync (missing file, no backup) are settled and the next one is tried. **Ending SubSync early** restores every item that has no result: a user cancel (the cancelled item is `cancelled`, no record), a time limit (that item `failed` "timeout"), Jellyfin stopping (`cancelled`, no record; the rest stay queued), SubSync exiting on its own (`failed`, exit 7 stops the queue as today). **Change 1:** `serve` can't cancel one item, so a cancel or time limit of one item ends the process, and the *other* item goes back to the head of the queue untried (restored, no record, no crash count); the next item starts a new process. **Change 2:** an item's time limit (D34) starts at its first stage after `queued`, or at the `result` of the item sent before it, whichever comes first (at once when nothing else was in SubSync), so waiting behind the other item doesn't count. One crash counts once toward D14. **Refused requests** (immediate `failed` result with a reason) fail that item only. **Fallback:** SubSync 1.2.0, an unreadable version, or `serve` not starting (start failure, or an exit other than 7 before `ready`) run the rest of that queue run with one `sync` per item (D5); a setup that never gets `ready` within the item's time limit is a timeout. Startup recovery, the Job Object and the leftover-run record (D29) are unchanged; the record holds the `serve` process | Start-up (self-check, Python, both models) is paid once per queue run instead of once per item, and each item's audio is read while the previous one is listened to. The gain is not measured yet: the Jellyfin log's line "queue run finished: N item(s) through K SubSync process(es) in S s" is there to compare a season with Phase 1 (`M0-LIVE-CHECKS.md`). Sending at `listening` (not earlier) keeps at most one item waiting, which SubSync's README says is enough for the overlap and keeps the restore set small. The page's `current` stays the older item; the item sent ahead also shows as `running`, stage `queued` (API.md) |
